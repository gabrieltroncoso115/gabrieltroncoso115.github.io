Sistema de diseño para Pepper

Lideré la creación de un Design System MVP para reducir inconsistencias y alinear el trabajo entre diseño y desarrollo mientras el producto continuaba evolucionando.

RolLead UX/UI Designer
ProductoSaaS financiero
Periodo2023—2025
ColaboraciónDev · Stakeholders · Marketing
Contexto del producto

Gestión financiera desde una sola plataforma.

Pepper es una plataforma de gestión financiera en la nube orientada a empresas que necesitan controlar su flujo de caja y tomar decisiones con mayor visibilidad.

El producto permite proyectar ingresos y egresos, pagar proveedores, conciliar movimientos bancarios, automatizar cobranzas y analizar información mediante un dashboard. También ofrece una API para conectarse con otras herramientas.

El desafío

El crecimiento había fragmentado la experiencia.

Distintos equipos resolvieron necesidades urgentes utilizando Bootstrap, otros frameworks y componentes propios. El resultado fue una interfaz con patrones visuales y de interacción inconsistentes.

01

Acciones inconsistentes

Acciones similares se presentaban y utilizaban de forma diferente según la sección.

02

Patrones dispares

Estados de botones, tablas, formularios y modales no compartían una misma lógica.

03

Trabajo repetido

El equipo debía redefinir estilos y corregir problemas de interfaz al desarrollar nuevas funcionalidades.

1 · Auditoría

Antes de diseñar, había que dimensionar la deuda.

Documenté los flujos prioritarios en FigJam y construí un inventario de componentes para agrupar variantes, inconsistencias y soluciones repetidas.

2 · Hallazgos

Más de tres soluciones técnicas sin reglas comunes.

La auditoría mostró que un UI Kit visual podía ayudar, pero no resolvería por sí solo las diferencias de navegación, interacción y correspondencia con el código.

3 · Decisión de alcance

De una biblioteca visual a un sistema adoptable.

El plan inicial era entregar un UI Kit. Durante el análisis concluimos que necesitábamos reglas, tokens y documentación que acompañaran la migración gradual del producto.

01

Gobernar de lo macro a lo micro

Definir jerarquías, navegación y estados, además de componentes visuales.

02

Permitir una evolución progresiva

Crear reglas para integrar nuevas funcionalidades sin bloquear el desarrollo existente.

03

Alinear Figma y front-end

Mantener correspondencia entre nombres, tokens, variantes y estados utilizados por ambos equipos.

4 · Fundamentos

TailwindCSS como lenguaje compartido.

Con la adopción de TailwindCSS durante el proceso, definí los tokens siguiendo su nomenclatura para reducir diferencias entre las decisiones de diseño y su implementación.

5 · Componentes y documentación

Componentes atómicos conectados con flujos reales.

Construí componentes atómicos, variantes, estados y ejemplos de uso. En paralelo, utilicé estos fundamentos para definir patrones de navegación de nuevas funcionalidades.

El trabajo se revisó en ciclos con desarrollo, stakeholders y marketing para ajustar decisiones y mantener la documentación alineada.

Alcance y límites

Un MVP preparado para continuar evolucionando.

El trabajo produjo una auditoría de flujos y componentes, fundamentos como variables de Figma y una librería documentada en Figma y Storybook.

Sobre el impacto

No cuento con métricas cuantitativas para afirmar una reducción del tiempo de desarrollo o de la curva de aprendizaje. Esos efectos fueron objetivos esperados del sistema y quedaron como parte de los próximos pasos de medición.

Próximos pasos identificados

  • Medir uso, satisfacción y adopción del sistema.
  • Incorporar feedback de soporte.
  • Continuar evolucionando los patrones de interacción.
  • Realizar pruebas con usuarios finales.

Aprendizaje principal: comenzar por tokens y documentar utilizando el lenguaje del equipo de desarrollo facilita que el sistema pueda adoptarse gradualmente.
